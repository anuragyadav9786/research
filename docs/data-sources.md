# ThinkFin Data Sources

Every number the platform ever shows a user must be traceable to one of the
two categories below — real ingested data, or explicitly labelled sample
data — never a blend presented as if it were one thing (Rule 2/3).

## 1. Sample / development data (currently in use)

**Source**: `database/seeds/seed_sample_data.py` — a script in this repo,
not an external provider.

**What it is**: entirely fictional AMCs, schemes, securities, managers and
NAV/benchmark history, generated by a seeded random walk
(`numpy.random.default_rng(42)`). It exists solely to exercise the schema
and analytics engine end to end during development.

**How it's kept identifiable**: every name is invented ("Northbridge",
"Meridian", "Sample Bank Corp Ltd", ...), every identifier is prefixed
`SAMPLE-`/`SMP`, and its `data_sources` row is named
`"Synthetic Sample Data Generator"` / `source_type="manual"` — so a query
against `nav_history.source_id` always reveals whether a given NAV point
came from this generator or from real ingestion.

**Must never**: be presented in a production UI as if it were a real fund,
or be left in a database that also holds real ingested data without a
clear way to tell them apart (see the script's `--reset` flag, which only
touches its own sample rows).

**Market regimes are sample data too.** The 4 rows the seed script writes
to `market_regimes` (`"Sample Regime — Recovery/Bull"`, `"— Correction"`,
etc.) are illustrative date windows picked to match the shape of this
*same synthetic* NAV/benchmark series — they do not assert anything about
real historical market conditions in those calendar dates. Every API
response built from them (`GET /api/funds/{id}/market-regimes`, `GET
/api/market/regimes`) repeats this as an explicit `methodology_note` so
it's never mistaken for verified market history. Real regime
classification against real index data is unbuilt — see section 3 below.

## 2. AMFI NAVAll.txt (real source — architecture built, live fetch unverified)

**Source**: Association of Mutual Funds in India, `https://www.amfiindia.com/spages/NAVAll.txt`
**Source type**: `amfi` (see `data_sources` table)
**Update cadence**: once per business day (AMFI's own publishing schedule)
**License / access**: publicly published, no API key or registration
**Format**: semicolon-delimited text, one row per scheme variant, grouped
under alternating AMC-name and category-header lines. Documented in full
in `data_pipeline/sources/amfi/parser.py`'s module docstring.

**What this pipeline does with it**:
1. `data_pipeline/sources/amfi/client.py` downloads the raw file.
2. `data_pipeline/sources/amfi/parser.py` parses it into structured rows.
3. `data_pipeline/validation/nav_validation.py` rejects (with a specific
   reason) any row with a missing field, non-numeric or non-positive NAV,
   an unparseable date, an "N.A." NAV, or a duplicate scheme code within
   the same file.
4. `data_pipeline/normalization/scheme_mapping.py` matches each accepted
   row to an existing `scheme_variants` row by AMFI code (falling back to
   ISIN). **A NAV file alone never creates a new scheme** — see that
   module's docstring for why.
5. `data_pipeline/storage/database_writer.py` upserts matched rows into
   `nav_history` (`ON CONFLICT DO NOTHING` on `(scheme_variant_id, date)`,
   so re-running for an already-ingested date is a safe no-op).
6. Every run — success or failure — is logged to `data_ingestion_runs`
   with download/accept/reject counts and, on failure, an error message.

**Current status — IMPORTANT**: this sandboxed development environment's
network policy blocks outbound HTTPS to `amfiindia.com` (confirmed via a
403 policy denial on the CONNECT request, visible in the agent proxy's
diagnostics). As a result:
- The parser, validator, scheme-mapping, storage-writer, and full
  orchestration logic **have been tested and verified** — the integration
  test in `backend/tests/integration/test_nav_ingestion.py` runs the
  entire pipeline against the real local Postgres database (with the
  network call itself replaced by a synthetic fixture matching the real
  file format), including idempotency and failure-logging behaviour.
- The HTTP client's error handling (timeout, HTTP error status, empty
  response) is unit-tested against a mocked transport.
- **What has not been verified**: an actual successful download from
  `https://www.amfiindia.com/spages/NAVAll.txt`. This must be run from an
  environment with outbound internet access before Phase 3 is considered
  fully done — e.g. `python -m data_pipeline.orchestration.daily_pipeline`
  from a normal developer machine or a CI runner with unrestricted egress.
